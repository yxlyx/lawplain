# Private research architecture (#189)

## Canonical model

`saved_authorities` is the owner/document root for the private library. A root may represent an explicit bookmark (`savedAt` is non-null), one or more annotations, or both. `passage_annotations` belongs to a root through an owner-bound composite foreign key. Active and still-restorable `saved_quotes` rows are migrated into this model. Quote IDs are retained as annotation IDs where the location is unique; owner-scoped aliases preserve every old private quote link when canonical deduplication chooses another ID. `saved_quotes` is legacy after migration: annotation creation and note editing never mirror into it, compatibility DELETE/restore only synchronizes tombstones, and permanent annotation deletion purges every mapped legacy row and alias.

Captured source material is immutable: document identity, title/citation/path, exact text, anchor, offsets, and surrounding context are not editable annotation fields. Only the user's own note (up to 10,000 characters) and the annotation's label are editable. Anchors are snapshots and may become stale when a source changes; clients must retain the captured text/context, report that state, and never silently move an annotation to a merely similar passage.

## Anchoring and staleness

Every annotatable block carries two data attributes. `data-section-id` names the section that contains the block; `data-quote-anchor` names the block itself. Judgment blocks receive both in `renderBlock` (`src/components/JudgmentBody.tsx`), where the section id comes from the backend's section offsets and the block anchor is the parsed block's key. A statute section is its own block, so the `<article>` rendered by the statute page carries `s-<section_no>` as both, and `StatuteSectionShell` hosts the same resolution machinery around it. A capture never spans blocks — `SelectionTools` rejects a selection whose start and end resolve to different `[data-section-id]` blocks — and stores that block's `data-quote-anchor` (falling back to its section id), the exact selected text, the selection's character offsets within the block's text, and 300 characters of context on each side.

`findPassageRange` (`src/lib/passage-anchor.ts`) resolves that locator against the live DOM. It first considers blocks whose `data-quote-anchor` equals the stored anchor, then blocks whose `data-section-id` is the stored anchor or one of the caller's fallback section ids — the second pass is what lets a locator written before block anchors existed, or one whose block anchor has since changed, still resolve inside its section. In both passes the exact captured text must still be present in the block. Context scoring, the longest matching suffix of `contextBefore` plus the longest matching prefix of `contextAfter`, only chooses between repeated occurrences of that same text, with the stored offsets breaking a tie. Nothing else is fuzzy: if the passage was edited, resolution returns `null`.

Judgments and statutes therefore fail differently. A statute page renders every section server-side in one pass, so a passage that does not resolve there means the source changed. A judgment body loads its text in 60,000-character pages, so a passage that does not resolve may simply not be loaded yet; the client requests the next page and retries as text arrives.

A client reports exactly three states. *Anchored* — a range resolved. *Pending* — the document has more text to load or has not finished rendering, so this is not the last attempt. *Orphaned* — everything is loaded and the exact text is gone. Staleness is computed client-side, per render, from the document in front of the user; it is never persisted, there is no stale column, and a passage that failed against a partially loaded judgment must not be recorded as orphaned. An orphaned annotation keeps its note, label, and captured text and stays listed and deep-linkable; it only loses its place in the text. Painting is skipped entirely where the CSS Custom Highlight API is unavailable (`supportsHighlightApi`), which is a rendering limitation and not a stale anchor.

## Duplicate, adjacent, and overlapping passages

`idx_passage_annotations_owner_location` (migrations/0020, lines 37-40) makes `(userId, authorityId, anchor, startOffset, endOffset, exactText)` unique, so an exact duplicate cannot exist. Saving the same passage again is an upsert: the newer write applies its label, keeps the existing note unless it carries one, clears a pending tombstone, and advances `updatedAt`. Highlighting a passage a second time under a different label relabels it; it never creates a second record and never silently drops a note.

Adjacent and overlapping ranges differ in their offsets, so they stay distinct annotations with their own notes and labels. The model does not merge, split, extend, or reorder them. Where two highlights overlap visually the CSS Custom Highlight API paints the higher-priority registration, and the annotation whose card is open is registered as `lawplain-annotation-active` above the per-label highlights, so the passage the user is working on is the one that reads clearly.

## Labels, tags, and collections

A label classifies one passage. This phase ships a single universal preset, the case-reading set from #193 — Key point, Facts / Procedure, Issue, Rule / Holding, Reasoning, Exception / Counterpoint, Follow up — for judgments and statutes alike, because a statute-specific preset is a labelling decision rather than a storage one. `key-point` is the default: it is what a plain highlight with no explicit choice stores, and what migration `0021` backfills onto annotations that predate labelling.

The column is length-bounded rather than enum-bounded, `CHECK (length(label) BETWEEN 1 AND 64)`, so the user-defined labels of #193 proper can land without a table rebuild. The accepted set therefore lives in `src/lib/annotation-labels.ts`, and writers and readers treat it asymmetrically on purpose. A write carrying an unrecognised id is rejected, so a client bug cannot quietly mislabel a passage. A read carrying one — a user-defined label from a newer client, or a label since archived — resolves to a readable fallback name and a neutral highlight token, so the passage stays visible and editable instead of vanishing from the document. Colour never carries meaning on its own: every surface that paints a label's colour also renders its name, and each colour has a solid `-ink` companion for chips, swatch rings, and the highlight underline.

Tags and collections remain distinct from labels and remain deferred (#197). A tag is the user's own vocabulary, free-form and many-to-one against a document root; a collection is an owner-scoped ordered grouping of roots. Both attach to the canonical root rather than duplicating source records, and both must enforce owner-bound foreign keys and owner-local uniqueness when they land.

## Ownership, time, and pagination

Every query and mutation is scoped by authenticated `userId`, including prepared statements in D1 batches. Annotation foreign keys include `userId`; a foreign or nonexistent ID has the same 404/null result. List APIs use bounded keyset pagination. Cursors encode the owner and complete query shape as well as the last ordering key — `updatedAt` for annotations, `activityAt` for library roots — and its `id`, and are rejected when replayed for another owner or query.

The timestamps have distinct meanings:

- `createdAt`: when the root or annotation first entered the library; never rewritten.
- `savedAt`: when the document was explicitly bookmarked; nullable. Saving sets it only when absent, and unsaving clears it.
- `activityAt`: latest private-library activity used for ordering. Annotation creation/note edits and explicit saves advance it without changing `savedAt` unnecessarily.

## API boundary

Every private endpoint requires a session, derives `userId` from it, and answers through `privateJson`.

`GET /api/annotations` lists the owner's annotations most-recently-updated first, optionally filtered by `docType` and `docId`, with `limit` and an opaque `cursor`. `POST /api/annotations` creates one from a captured locator plus an optional `note` and `label`, answers 201, 400 for any invalid field, and 409 when the write raced a permanent deletion of the same document. `GET /api/annotations/[id]` returns one annotation or 404. `PATCH /api/annotations/[id]` accepts only `note` and `label`; captured source material is immutable, so any other key is a 400 rather than a silent no-op, and an omitted field is left alone so relabelling cannot clear a note and vice versa. `DELETE /api/annotations/[id]` is permanent. `GET /api/library` lists document roots by `activityAt` with their live annotation counts, under the same limit and cursor rules.

`/api/quotes` and `/api/quotes/[id]` are the legacy surface over the same canonical rows: the old quote shape (`sourceTitle`, no note), a fixed 100-row list, legacy ids resolved through the alias table, and the 10-second `DELETE`/`POST` Undo that pre-migration clients still depend on. New clients use the annotation endpoints.

## Limits

Enforced in `src/lib/private-annotations.ts`, and mirrored by CHECK constraints where a column can express them: note 10,000 characters; exact text 1 to 5,000; `docId`, `title`, `citation`, and `anchor` 500 each; `contextBefore` and `contextAfter` 1,000 each; label id 1 to 64. A page is 25 rows by default and 100 at most; an oversized request is clamped rather than rejected. Offsets must be safe integers whose difference equals the exact text's length, and the path must be an internal `/judgment/` or `/statute/` path. The selection toolbar captures 300 characters of context on each side; the stored bound is deliberately larger so a richer capture needs no migration.

## Deletion and migration

Deleting through the annotation API is permanent. It removes the canonical annotation plus every mapped legacy quote and alias. An annotation-only root is removed once its last annotation is permanently deleted; unsaving removes a root only if it has no annotations. For deployment compatibility, the legacy quote DELETE/restore endpoints use a 10-second canonical annotation tombstone so cached clients can honour their existing Undo promise. They tombstone or restore the canonical annotation and every owner-scoped mapped legacy row in one D1 batch. Recent pre-migration tombstones are copied so Undo also survives the worker handoff, while already-expired legacy tombstones and their selected text are purged during migration. Owner-scoped quote, annotation-list, and library reads opportunistically purge later-expired tombstones, mapped legacy rows, aliases, unused guards, and empty annotation-only roots after first writing a deletion watermark; explicit saves survive. New annotation clients never expose that soft-delete contract.

Migrations run before the new worker deploys, so migration `0020` includes a one-way compatibility bridge for overlapping old workers. Legacy-shaped authority writes receive explicit-save timestamps, and causally current legacy quote inserts/deletes/restores are mirrored into canonical annotations. Old-worker deletes synchronize every legacy ID mapped to the canonical annotation, while expired or stale restores are rejected before `UPDATE ... RETURNING` can report success. Guard rows prevent an old worker's hard unsave from cascading through annotations; canonical final-annotation deletion removes the guard in the same D1 batch. A document-level deletion watermark, containing no selected text, rejects already-started old-worker or canonical inserts that arrive after permanent deletion. Guards, aliases, and watermarks all bypass or cascade with account deletion, so account deletion still removes roots, annotations, compatibility metadata, legacy quotes, and future labels/tags/collections.

## Privacy, export, and AI

Four decisions from #189 bind every private surface, present and future. `userId` is derived from the server session alone and is never accepted from a request body, query string, or path. An id the caller cannot access receives exactly the response a nonexistent id receives, so annotation ids do not enumerate. Annotation text — captured passages and notes alike — is excluded by default from analytics, application logs, public search, shared links, and Ask Lawplain; failing private requests answer with a generic error rather than logging a private payload, section-engagement analytics carry document, section, and search-term identifiers but never passage or note text, and a shared `?savedQuote=` link resolves the passage through an owner-scoped endpoint, so it reveals nothing to another account. This phase ships no public or team visibility: an annotation is visible to its owner and to nobody else.

Every private API response, including authentication, validation, conflict, and not-found errors, is `private, no-store` and carries no-cache and no-index headers. Private research must not enter shared/CDN caches. A future account export should include canonical roots, timestamps, immutable source snapshots, notes, and organisation metadata in a documented portable format; legacy quote rows are not a second export source after migration.

Private source text and notes are never sent to an AI feature implicitly. Each AI operation requires explicit, purpose-specific user consent. Stored AI output must record provenance: consenting user, selected source/annotation IDs, model/provider, prompt or policy version, creation time, and enough transformation metadata to audit the result. Consent for one operation is not blanket consent for later training, retention, or unrelated processing.
